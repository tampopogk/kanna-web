# Cut the Kanna marketing site back to a simple, confident page

## Goal

Rebuild `index.html` so it reads as a small, confident product page: the old
pre-refresh site's hero atmosphere (gradient, perspective grid, scanline
overlay) on top of the current site's cleaner layout, one product screenshot, a
plain feature list, the mobile captures, and nothing else. The owner's
complaint is that the current site "reads as obvious AI slop" and that the old
site — "mostly a cool background plus download links" — was better.

- One hero image only: `assets/kanna-desktop.avif`.

  App Store QR code and a text link.

- The numbered feature cards ("Give autonomy a shape", 01–04).
- The Define/Run/Review/Handoff illustration section.

  caption. The standing directive forbids passing fabricated UI off as a

`support/index.html`, the four existing files in `assets/`.

## Screenshots and the capture harness

The owner asked for a capture harness in this repo, with a seed of my own, and
for it to be used for the screenshots. `tools/capture/` is that harness. It
works end to end; what it does not yet produce is a *good* screenshot, and the
reason is worth recording.

### Why not the kanna repo's e2e seed

`kanna/apps/desktop/tests/e2e/seed.sql` seeds three repositories and fourteen
tasks. Its **task titles are good** — "Refactor auth middleware", "Rate
limiting middleware", "Webhook delivery system", "DB schema migration v3". Its
**repository names are not**: `example-app`, `example-api`, `example-docs`,
under `/Users/test`. Repository names are the most prominent text in the Kanna
sidebar, so captures from that seed put the word "example" in front of every
visitor. `tools/capture/seed.sql` is the same idea with homepage names:
`orchard-web`, `orchard-api`, `fieldnotes`, and ten tasks of the same shape.

### What the harness does

- `fixtures.sh` creates real git repositories and a real worktree per task.
  This is not optional: Kanna reconciles its database against the filesystem,
  and the first seeding attempt had every task closed and moved to the `done`
  stage within seconds because the worktrees did not exist. The tasks only
  survive once the branches and worktrees are real.
- `seed.sh` substitutes the fixture root into `seed.sql` and refuses to run
  against `kanna-v2.db`.
- `capture.mjs` drives the app over the WebDriver server from
  `tauri-plugin-webdriver` and asks the app for its own screenshot.
- `convert.sh` produces AVIF and prints intrinsic sizes for the markup.

A **debug build is required**: `apps/desktop/src-tauri/src/lib.rs` initialises
the WebDriver plugin under `#[cfg(debug_assertions)]`, so the installed release
app cannot be driven.

### Isolation, and what it was isolated from

The owner's live instance is **Kanna Staging.app**, and it is running this very
task, so a second instance had to be provably separate. It was: its own
database (`kanna-capture.db`, with `kd` refusing production `kanna-v2.db`), its
own `KANNA_DAEMON_DIR`, and its own ports (1520 / 4555 / 9180 / 48220 / 8181 /
4655, all verified free first). The build was run under a `Cargo.lock`
checksum guard because that checkout had uncommitted changes; the checksum was
unchanged afterwards. Shutdown used `kd dev down` and then a kill of the single
daemon PID under this task's build path. **`kd dev down --kill-daemon` was
deliberately not used**: it reaps daemons, and four other tasks' daemons were
live on this machine. Kanna Staging was confirmed still running afterwards.

### What came out, and why it is not on the page

The seeded task list renders correctly and reads well: three plausible
repositories, stage groupings, real task titles. But the right-hand pane is
empty, because an attached agent session is what fills it and no agent is
running. The existing hero capture has a live terminal in that pane; the new
one has a blank half. Adding a half-empty screenshot to a page that was just
cut back for looking padded would make the page worse, so **no new capture was
wired in**.

Two automation limits found on the way, recorded so the next attempt does not
rediscover them: the command palette is **⇧⌘P**, not ⌘K, and neither synthetic
`KeyboardEvent`s nor the WebDriver actions API opened it — its shortcut context
wants main-window focus that injected keys did not reach. `⌘/` opens the
keyboard-shortcuts overlay, which must be dismissed before capturing.

**What would finish it:** something real in that right-hand pane. Either an
agent session actually running against a fixture worktree, or a shell tab with
genuine output. Both are real UI and neither is fabricated; both need either
UI automation that reaches the main window or a person driving the dev
instance. Referred to the owner rather than solved by faking pane content,
which the standing directive forbids outright.

split the page into two unrelated halves. All four product captures are of a
dark app, so they sit on a dark page without a frame fighting them.

Lifted from the old file: the `180deg` `#1a0533 → #3d0e62 → #e8357a → #ff8c00`

and the buttons, and a plain naming eyebrow instead of a slogan.

## QR code

`assets/kanna-mobile-qr.svg` encodes `https://apps.apple.com/app/id6802176590`.

- Generated locally with `segno` (version 3, error correction M, 4-module quiet
  zone, 296×296 intrinsic, dark `#12000f` on white), installed into a throwaway
  virtualenv under the ignored `.tmp/`. No third-party QR service is called at
  build time or at runtime.
- **Verified by decoding it back**, not just by generating it: a PNG render was
  read with OpenCV's `QRCodeDetector`, which returned
  `https://apps.apple.com/app/id6802176590` exactly.
- It sits on a white plate because scanners expect dark modules on a light
  field; the page around it is near-black.
- Marked up with explicit `width="296" height="296"`, `loading="lazy"`,
  `decoding="async"`, and alt text naming the destination. The visible text
  link beside it points at the same URL.
- An HTML comment above the block records the same contract, so the next editor
  does not swap it for a runtime generator.

If the URL ever changes, regenerate the SVG the same way and update the `href`,
the alt text, and the comment together.

## Verification

Served locally on port 8137 and driven with headless Chrome over the DevTools
protocol, so the viewport could be emulated properly — plain
`--headless --window-size` clamps its layout viewport to 500px wide, which
produces cropped screenshots that look like overflow bugs and are not.

**Download script — works; the constant was left unchanged.**
`https://api.github.com/repos/jemdiggity/kanna/releases/latest` answers `301`
to `https://api.github.com/repositories/1185799373/releases/latest`, which
resolves to the transferred `tampopogk/kanna` repository. `fetch()` follows
redirects by default and the redirect stays on `api.github.com`, so CORS is
unaffected. In the browser, both buttons receive real URLs —
`https://github.com/tampopogk/kanna/releases/download/v0.2.0/Kanna_0.2.0_arm64.dmg`
and `…_x86_64.dmg` — and the version label reads
`v0.2.0 · Requires macOS 15 or later`. Per the task's instruction to change
nothing if it works, `REPO` still reads `jemdiggity/kanna`.

**No horizontal scroll.** At 1440, 768, 390 and 320 CSS pixels,
`document.documentElement.scrollWidth` equals `window.innerWidth`, and a sweep
of every element in `<body>` found none whose right edge exceeds the viewport.

**Visual.** Desktop (1440×900) and mobile (390 wide, full page) renders
inspected: hero gradient, grid and scanlines present; one screenshot; five
feature rows; three phone captures; QR and store link; footer. The feature list
collapses to one column below 820px and the phones stack below it.
