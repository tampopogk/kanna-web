# Run the Kanna task-manager singleton on Claude

## Goal

Make this repository's Kanna task-manager singleton spawn on the Claude provider (Fable on this machine) instead of Codex, changing nothing else about the repository's workflow or agent choices.

## Context

- The built-in `task-manager` agent declares `agent_provider: codex, claude, copilot, opencode, antigravity`, so a fresh singleton resolves to Codex by default.
- The live Task Manager task `9b431d85` (workflow `singleton-task-manager`, branch `task-9b431d85`) is running on Codex. A running singleton keeps the session it was spawned with, so its provider cannot change in place.
- Kanna reads `.kanna/agents/**` and `.kanna/config.json` from the `origin/main` snapshot of the registered checkout, never from a task worktree. Only `.kanna/config.local.json` is read from the registered checkout's working tree.
- Kanna offers two repository-supported ways to change an agent's provider. The `agentProviders` map in `.kanna/config.json` is consulted at spawn time and wins over the definition, but the agent listing (`kanna_list_agents`) reports only the layered `AGENT.md` + `EXTEND.md` definition and ignores that map. A repo-local `.kanna/agents/<name>/EXTEND.md` with `agent_provider` frontmatter replaces the built-in's provider list in the resolved definition, so both the listing and spawn resolution agree.

## Decision

Add `.kanna/agents/task-manager/EXTEND.md` with frontmatter `agent_provider: claude, codex, copilot, opencode, antigravity`. This is the task-manager agent override; it makes the resolved `task-manager` definition report `defaultProvider: claude` (source `repo_override`) and puts Claude first in spawn-time resolution while keeping the stock fallback order. No `.kanna/config.json`, workflow, or flavor selection is added, and no other agent is touched.

Precedence reminder: an explicit `agent_provider` on `kanna_signal_agent`, or an `agentProviders` entry in `.kanna/config.json` / the machine-local `.kanna/config.local.json`, would still outrank this override. None exist for this repository today.

## Lifecycle action after this reaches origin/main

Kanna has no "restart singleton" action. The safe sequence is:

1. Confirm `origin/main` contains this change and that `kanna_list_agents` for repo `repo-18d1e21129cdc470` reports `task-manager` with `defaultProvider: claude` and `source: repo_override` (the listing cache refreshes within about 30 seconds of the remote-tracking ref moving; task creation does its own `git fetch`).
2. Make sure task `9b431d85` is not mid-action: its `runtimeState` should be `idle` (or `exited`), and no merge handoff or revision it is coordinating should be in flight.
3. Retire it with `kanna_close_task {"task_id": "9b431d85"}` (or the desktop close action). Closing kills its session, snapshots any dirty worktree state into a local WIP commit, removes its worktree, and keeps branch `task-9b431d85`. Once `closed_at` is set the singleton lookup no longer sees it.
4. Recreate the singleton by triggering the repository's Task Manager command in the desktop, or `kanna_signal_agent {"repo_id": "repo-18d1e21129cdc470", "agent": "task-manager", "message": "Run as this repository's long-running Kanna task manager. Survey the active work, then continue the event loop and coordinate whatever needs attention."}`. The response's `created: true` confirms a fresh task; its `agentProvider` should read `claude`. Passing `"agent_provider": "claude"` on that call is a belt-and-braces override and is only honoured for a task the call creates.
5. If the recreate reports the singleton as already owned (`created: false` or a duplicate/owned error), wait for the account-wide singleton directory to reconcile the closed task and retry rather than creating a rival task.

Do not close `9b431d85` before the change is on `origin/main`; a singleton recreated earlier would resolve from the old snapshot and come back on Codex.

## Validation

Kanna only reads agent definitions from `origin/main` of a registered checkout, so the change could not be observed on `kanna-web` without publishing. It was validated instead against a throwaway snapshot on 2026-09-03: this branch's commit was pushed to a local bare repository under `.tmp/`, cloned so that `origin/main` carried the change, and the clone was registered with Kanna as `kanna-web-provider-probe` (repo `repo-18d1eb288e0dae30`). `kanna_list_agents` for that repo reported:

| agent | defaultProvider | source |
|---|---|---|
| task-manager | claude | repo_override |
| ship | codex | built_in |
| every other built-in | claude | built_in |

The same call against the real `kanna-web` repo (`repo-18d1e21129cdc470`) still reports `task-manager` as `codex` / `built_in`, which is expected until this commit reaches `origin/main`. The probe registration can be removed from the Kanna sidebar; Kanna exposes no repo-removal tool, and its checkout lives under this task's ignored `.tmp/` directory.

Other checks: `git check-ignore .tmp` confirms the scratch directory is ignored, `git ls-files .kanna` shows the override is tracked, and no JSON or shell files were added, so no schema or `sh -n` validation applied.

## Done when

The `EXTEND.md` override is committed on this branch, the resolved `task-manager` definition reports `defaultProvider: claude` from a snapshot that contains the change, the lifecycle action above is documented, and nothing is pushed or deployed from this task.
